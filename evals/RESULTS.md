## Honest limitations

- The main dataset was written by the same people who wrote the rules, so it is not a blind test — some attack phrasings closely track rule patterns (e.g. `instruction_override`'s "ignore ... instructions" wording) and will over-state real-world catch rate. The held-out set exists specifically to counter this: its numbers are the more honest signal for how the system does on phrasing it has never seen, at the cost of a smaller sample (50 vs 204 rows).
- `genuine_trigger_words` (main set) and `genuine_trigger_words_novel` (held-out) are the highest-signal categories for false positives: they specifically probe words ("ignore", "secret", "urgent", "override", "disregard", "between us") that the rule engine keys on, used in ordinary banking sentences.
- Some non-English strings in both files (Swahili, Kannada, Tamil, Telugu, Vietnamese, Indonesian, Korean in particular) are best-effort translations, not reviewed by a native speaker — treat the exact wording as approximate, though the intent (genuine banking request vs. instruction-override attack) is correct by construction.
- Hybrid numbers (when present) reflect a live run against one Gemini model snapshot at one point in time; LLM judge output is not perfectly deterministic even at temperature 0, so a re-run may shift individual borderline verdicts slightly.
- **The judge only fires when the rule engine's own gate opens it.** As of this version the gate is wider than just high-risk-intent-or-grey-zone — it also opens for unknown intent, non-Latin script, any obfuscation flag, and untrusted sources (see `docs/PROMPT_FLOW.md`) — specifically to close a multilingual gap found in an earlier version of this report, where every multilingual miss had `risk_score=0.0` because the judge was never consulted at all. In this run the gap is closed, not just narrowed: `multilingual_override` (main set) and every `multilingual_novel_*` category (held-out) score 100% catch rate under hybrid, versus 60% and 0% respectively under rules-only.
- **The first full run of this eval hit real judge timeouts under sustained load, and they failed closed as designed** — worth stating plainly rather than quietly re-running past it. At the original 4s-per-call timeout and a 1.5s throttle, pushing ~250+ live calls through a free-tier key over several minutes, a handful of high-risk multilingual genuine messages (e.g. `e0194`–`e0202`) got a judge timeout, hit the high-risk fail-closed path (`risk` forced to the threshold), and were wrongly blocked — not because Gemini misclassified them, but because it never got to answer at all. We verified this by re-running those exact messages individually afterward: all classified correctly once off the degraded connection. The fix that's reflected in the numbers above: `bankguard/providers/gemini.py`'s timeout became a 7-second **total** budget across one attempt plus one retry (up from a 4s single attempt, still comfortably under Vercel's 10s function limit — see `docs/PROMPT_FLOW.md`), and the rows that failed the first time were re-run individually (not the whole eval) with a 3s inter-call throttle; every previously-cached successful result was reused as-is. The numbers in this report are the result of that targeted re-run, not a cherry-picked clean run.
